## 先定义完成，再设计循环

一个智能体是否有用，首先取决于任务能否验收。把“帮我研究一下”改写成“整理三种方案，给出来源、约束与待确认项”，就能明确输入、产物和停止条件。设计时还要区分任务完成、等待用户和执行失败，避免把一段流畅的回答误当成工作已经结束。

开始实现前，可以用一个普通函数完成同样的任务。如果流程固定、分支很少，直接编排往往更易维护。只有当下一步需要结合环境信息判断时，才值得引入模型决策。

## 工具应当窄而明确

工具名称、参数和返回值组成了智能体与环境之间的契约。一个工具最好只承担一种职责，返回结构化状态、可验证的结果以及必要的错误信息。读取和修改应分开设计；把“检索草稿”和“发送消息”揉在一起，会让权限和测试都变得模糊。

外部网页和文档只能提供任务数据，不能获得修改任务或扩大权限的资格。执行层应独立检查授权，不能仅依赖模型在提示词中的自我约束。

## 给执行设置预算

步数、耗时和费用都需要边界。以下代码仅演示步数与截止时间检查，实际系统还应检查工具权限和资源预算：

```ts
type Budget = { stepsLeft: number; deadline: number };

function takeStep(budget: Budget): void {
  if (budget.stepsLeft <= 0 || Date.now() >= budget.deadline) {
    throw new Error("Execution budget exhausted");
  }
  budget.stepsLeft -= 1;
}
```

预算耗尽时，应保留已完成的结果并明确说明阻塞点。重试之前先判断操作能否安全重复；遇到发送、付款等有副作用的操作，不能因响应丢失就盲目再次执行。

## 让失败可以被检查

日志应记录任务标识、工具名称、耗时、错误类别和状态变化，避免记录密钥或不必要的个人数据。评估集除了成功案例，也应覆盖空结果、来源冲突、工具超时和用户中途取消。最终产物必须能追溯到证据，而不只是看起来合理。

## 上线前检查清单

- [ ] 完成条件可以由测试或人工直接验证
- [ ] 修改操作在执行层检查授权
- [ ] 超时、取消和预算耗尽都有明确出口
- [ ] 重试策略区分只读操作与有副作用的操作
- [ ] 日志经过脱敏，失败案例进入回归测试

先把一条真实任务路径做得可靠，再逐步扩大能力范围。清楚地知道何时停止，也是一种重要能力。
