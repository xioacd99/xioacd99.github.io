这是一篇演示文章，用于展示博客的内容和排版，不代表 Raymond 的真实项目或观点。

## 把发布看作一条流水线

静态博客的运行结构可以很简单，但内容、构建、部署和访问仍是四个不同环节。页面在开发服务器中正常显示，并不能证明线上地址也正确。可靠的流程应保存明确的输入与产物，让每一次发布都能追溯到某个提交。

[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages) 用于托管静态文件。需要运行时服务器处理的功能，应先确认是否适合这一托管方式，避免等到上线后才发现架构不匹配。

## 内容也需要校验

文章元数据建议包含标题、摘要、日期和标签，并为这些字段建立固定约束。日期格式不一致会影响排序，重复标识会造成路由冲突，空摘要则会影响列表阅读体验。发布前还应检查图片替代文本、链接目标以及代码块语言。

演示内容尤其需要清晰标记，防止读者把占位案例当作作者经历。可以同时使用显眼的正文说明和机器可读取的标记，让页面展示与构建检查采用同一份事实。

## 先检查生产构建

下面假设项目已经配置常规构建与预览脚本，并提交了 npm 锁文件：

```sh
npm ci
npm run build
npm run preview
```

预览时打开文章详情、标签页和不存在的路径，并直接刷新深层页面。锁文件可以帮助依赖安装保持一致，但不能替代对运行环境和构建输出的检查。

## 特别留意部署路径

项目站点可能位于仓库名对应的子路径下。应根据实际部署地址配置站点地址与基础路径，再检查导航、图片、样式和订阅链接是否一致。[Astro 的部署指南](https://docs.astro.build/en/guides/deploy/github/) 说明了 GitHub Pages 所需的路径配置与工作流设置。

持续集成中先运行检查和构建，成功后再部署同一份产物。部署完成也要访问真实网址；绿色工作流只能说明流程结束，不能替代浏览器中的阅读体验验证。

## 发布检查清单

- [ ] 元数据完整，演示文章有明确说明
- [ ] 全新安装依赖后仍能完成构建
- [ ] 首页和文章深层路径都可以直接访问
- [ ] 图片、样式和内部链接兼容基础路径
- [ ] 已记录部署提交，能够重新发布上一份已验证的内容

把这些检查变成固定习惯，发布就能从一次紧张操作，变成一条可以重复验证的日常流程。
